# План реализации Archivist для Codex

Дата исследования: 29 октября 2026 года. Это предложение по реализации; перечисленные архитектурные решения ещё не приняты.

## Цель и границы

Перенести основной цикл Archivist в Codex: собрать события задачи, выделить полезное знание, проверить его, сохранить в общей базе проекта и дать следующей сессии короткий релевантный контекст. Сохранить совместимость с Claude Code и существующим ledger.

Первый целевой продукт — локальный плагин Codex desktop с ручной установкой. Поддержку CLI проверять отдельно и заявлять только после живого прогона. Cloud и публикацию в общем каталоге вынести за пределы первого выпуска.

## Что уже есть

Фактическая версия в package.json и манифесте — 1.4.1; статус в начале README отстаёт. В PLAN.md перенос на Codex обозначен только пунктом после v1.

| Упаковка | scripts/build.mjs, plugin/, CI | Добавить независимую сборку Codex |

Проверено: 18 файлов тестов, 127 тестов проходят; npm run typecheck проходит. Реальная установка и события Codex в рамках исследования не проверялись.

Оставшиеся зависимости от Claude находятся не только в адаптере:

- PATHS в core/io.ts задаёт .claude/rules/archivist и .claude/skills.
- render.ts формирует frontmatter paths и использует эти пути при очистке файлов.
- pipeline.ts связывает seen с файлами правил через groupAreas.
- signals.ts распознаёт имена инструментов Claude: Bash, Read, Edit, Write и другие.
- CLI содержит Claude-specific doctor, baseline, подсказки и удаление файлов.
- Skills вызывают CLI через CLAUDE_PLUGIN_ROOT.
- Настройки анализатора используют haiku и предположения об учёте токенов Claude.
- Подключение OpenViking и UI-отчётность реализованы в моде; их перенос не получается автоматически из наличия общего ядра.

## Ограничения платформы

Официальная документация допускает пакет со skills и lifecycle hooks. Для нового пакета есть корневой plugin.json с OpenAI extension; .codex-plugin/plugin.json поддерживается как совместимый формат. Hooks требуют доверия пользователя; пакеты с hooks сейчас распространяются через ручную установку, а не общий каталог. Поэтому доставка плагина — отдельная задача от публикации в каталоге. [Упаковка плагинов](https://developers.openai.com/plugins/build/plugins).

Документированы SessionStart, UserPromptSubmit, PostToolUse, Stop, SessionEnd и фоновые command hooks. SessionEnd не является событием окончания каждого ответа. transcript_path может отсутствовать, а формат транскрипта нестабилен. Эти свойства требуют локальной очереди и толерантного парсера. [Hooks](https://learn.chatgpt.com/docs/hooks).

AGENTS.md имеет иерархию и лимит размера. Автоматическую загрузку .claude/rules с glob paths нельзя считать переносимой в Codex; вложенный AGENTS.md также нельзя считать полным аналогом такой загрузки. [Инструкции AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

## Предлагаемая архитектура

Один ledger и общее ядро; отдельные адаптеры выполнения и представления для двух агентов.

```text
Codex hook → нормализация → локальная очередь → worker
                                                ↓
                                общий анализатор + Llm adapter
                                                ↓
                                  ledger / proposals / metrics
                                                ↓
                                  представления и контекст Codex
```

Предлагаемые новые файлы:

```text
src/adapters/codex/hooks.ts
src/adapters/codex/events.ts
src/adapters/codex/transcript.ts
src/adapters/codex/worker.ts
src/adapters/codex/llm.ts
src/adapters/codex/context.ts
src/core/targets.ts
plugin-codex/plugin.json
plugin-codex/hooks/hooks.json
plugin-codex/bin/archivist
plugin-codex/skills/{setup,remember,decide,triage}/SKILL.md
```

Конкретные имена и число модулей уточнить после исследования событий. Не копировать всё ядро в новую ветку исходников.

## Этап 0. Проверить контракты Codex — 1–2 дня

1. Зафиксировать версии desktop/CLI и матрицу поддерживаемых сред.
2. Собрать минимальный локальный плагин-пробник и проверить установку, доверие hooks, PLUGIN_ROOT, права записи и доступность Node.
3. Снять обезличенные фикстуры SessionStart, UserPromptSubmit, PostToolUse, Stop, Interrupt и SessionEnd. Проверить turn_id, ошибки команд, apply_patch с несколькими файлами, exec_command/write_stdin и вызовы внутри functions.exec.
4. Проверить события подагентов: session_id может совпадать с родительским; определить реальные доступные признаки происхождения и не допустить двойного учёта.
5. Проверить additionalContext на SessionStart и допустимую доставку отчёта на следующем ходе. Не предполагать наличие toast, status line или API регистрации команд Claude.
6. Проверить поддерживаемый способ отдельного вызова модели с существующей авторизацией: доступность CLI, JSON-вывод, usage, timeout, отключение инструментов и hooks. Аналог fork считать отсутствующим, пока он не подтверждён.
7. Проверить sandbox, работу async hook после возврата управления и поведение при закрытии приложения.

Результат: docs/codex-spikes.md с фикстурами и таблицей «подтверждено / недоступно / требует обхода». Не сохранять реальные промпты и секреты в репозитории.

Условие перехода к полному автоматическому режиму: найден воспроизводимый способ анализа без повторного запуска hooks. Если его нет, выпустить ручной режим skills + CLI, а фоновый анализ оставить отдельным этапом. API с отдельным ключом — только явно настроенная альтернатива, без автоматического переключения на платные вызовы.

## Этап 1. Отделить целевую платформу — 1–2 дня

- Ввести TargetProfile для путей, рендера, загрузки контекста, генерации процедур и очистки. Общие пути .archivist оставить прежними.
- Сохранить текущий Claude profile по умолчанию для существующих проектов; добавить явный выбор codex или обоих профилей. Не определять его только по наличию установленного CLI.
- Отделить источник записи от списка активных представлений: изменение общего ledger должно обновлять все включённые представления.
- Убрать привязку атрибуции seen к groupAreas из общего pipeline; передавать подтверждённые загруженные entry IDs от адаптера.
- Нормализовать инструменты до существующего формата или добавить семантические операции read/edit/command. Для apply_patch учитывать каждый изменённый файл; не сохранять текст патча.
- Сделать doctor, baseline и uninstall зависимыми от выбранной платформы. Отсутствие claude не должно ломать Codex doctor.

Готово, когда один ledger можно отрендерить для двух агентов, Codex-операция не создаёт .claude/, а существующие тесты и поведение Claude сохранены.

## Этап 2. Рабочий ручной плагин — 1–2 дня

- Добавить Codex manifest и независимую сборку plugin-codex. Общий CLI собирать из одного исходника.
- Адаптировать remember, decide и triage под подтверждённый способ нахождения CLI; не рассчитывать на bin в PATH без проверки.
- Добавить setup: выбрать проект, включить профиль Codex, объяснить и проверить необходимые hooks, выполнить doctor.
- Процедуры генерировать в .agents/skills/archivist-*/SKILL.md с проверкой обнаружения в реальном Codex.
- Для первого выпуска подавать ограниченный core-контекст через SessionStart. Полные ADR и индекс хранить в .archivist, scoped-знания получать через recall по запросу и путям.
- Если hooks недоступны, setup может добавить небольшой управляемый блок в AGENTS.md с инструкцией прочитать core-файл и использовать recall. Обновлять только собственный блок, сохранять остальной текст; учитывать AGENTS.override.md и повторный setup.
- Не создавать автоматически вложенные AGENTS.md для произвольных glob scopes. Точный механизм автоматической подачи scoped-контекста решить по результатам этапа 0.

Готово, когда в чистом проекте установка → setup → remember → новый чат → recall работает, decide создаёт ADR с причиной, triage применяет или отклоняет предложение, а удаление сохраняет пользовательские файлы.

## Этап 3. Сбор событий и устойчивая очередь — 2–3 дня

- Hook-процесс выполняет только короткий локальный I/O: валидация payload, нормализация, маскирование и запись события. Целевой p95 обработчика после старта процесса — менее 100 мс; полную задержку измерять отдельно.
- Использовать ключи с namespace агента, session/turn и подтверждёнными идентификаторами событий. Старые ID не менять.
- UserPromptSubmit и Stop формируют границы ходов. Idle-задержка объединяет несколько ходов в задачу; Interrupt сохраняет незавершённое состояние, SessionEnd только завершает/ставит в очередь доступную работу.
- Хранить очередь, checkpoints и журнал в .archivist/.local/codex/. Добавить атомарную запись, блокировки и восстановление после обрыва; использовать существующие primitives там, где хватает их гарантий.
- Worker перепроверяет idle deadline и поколение сегмента перед анализом. Новый ход отменяет устаревшее задание.
- Обрабатывать задачу один раз при повторной доставке события и параллельных worker. Не полагаться на долгоживущий процесс hook; подбирать pending-задачи на следующем запуске.
- Транскрипт читать только из предоставленного пути, с лимитами объёма и поддержкой неизвестных записей; основой остаётся журнал событий. Отсутствующий транскрипт даёт явно отмеченный ограниченный режим.
- Распространить excludePaths на все источники, включая контекст транскрипта. Не читать файлы проекта ради реконструкции запрещённого содержимого.

Готово, когда прерывание, повтор Stop, два чата и перезапуск не теряют задачу, не создают дубли и не блокируют работу Codex.

## Этап 4. Фоновый анализ и отчёт — 2–3 дня

- Реализовать Llm.complete через способ, проверенный на этапе 0. Первый режим — digest; fork остаётся опциональной возможностью другого адаптера.
- Разделить настройки модели по провайдерам; не отправлять строку haiku в Codex. Проверять совместимость настроенной модели без жёсткой привязки к текущему списку моделей.
- Отдельный вызов получает только очищенный дайджест и отобранные записи. Ограничить его ответ схемой curator; лишить доступа к инструментам и записи в проект.
- Добавить timeout, отмену, ограниченное число попыток, backoff и защиту от рекурсивного самоанализа. ARCHIVIST_CHILD недостаточен, если runtime его не учитывает: проверить отключение hooks у дочернего запуска.
- Повторно использовать gate тривиальности, проверку evidence, дедуп, очередь review и ограничения автоприменения.
- Проверить семантику usage Codex. Отсутствующие токены и сведения о лимитах отмечать как неизвестные; не выдавать нули за наблюдения и не обещать соблюдение бюджета, который невозможно измерить.
- Оставить жёсткие лимиты размера дайджеста, числа анализов и конкурентности независимо от доступности usage. Вес cacheRead 0.1 считать внутренней оценкой, а не ценой Codex.
- Отчёт сохранять в файл; краткий результат показывать через подтверждённый канал следующего хода и команду/skill status. Не будить основной чат ради отчёта.

Готово, когда реальная нетривиальная задача даёт полезные записи либо обоснованный NOOP, тривиальная не вызывает модель, ошибка анализатора не ломает пользовательскую сессию, повторный запуск не меняет результат.

## Этап 5. Проверки и выпуск — 2–3 дня плюс наблюдение

- Unit/fixture-тесты нормализации событий, patch нескольких файлов, ошибок exec, неизвестного формата транскрипта и отсутствующих полей.
- Интеграционные проверки очереди: конкуренция, повтор события, новый ход во время idle, timeout, аварийный выход и восстановление.
- Проверки общих знаний: две платформы обновляют один ledger; очистка одной платформы не удаляет представления другой.
- Проверки контекста: бюджеты, scoped recall, загрузка в новом чате, неизменность пользовательского AGENTS.md и навыков.
- Сценарные eval: команда после ошибки, поправка пользователя, ADR с причиной, NOOP, секреты и excluded paths, отсутствие рекурсии.
- CI: существующие typecheck/tests, две сборки, проверка актуальности артефактов, схемы manifest/hooks и замкнутость путей внутри пакета. Живую проверку Codex добавить только при наличии воспроизводимого runner.
- Обновить README, CHANGELOG, матрицу совместимости, описание стоимости и ограничений. Выпуск выполнять по локальному навыку archivist-release-ci с расширением проверки на второй пакет.
- Провести неделю использования на 2–3 проектах. Оценивать долю NOOP, полезность записей, задержку hooks, расход анализатора, дубли и восстановление после ошибок. Метрики Claude и Codex разделять по источнику.

## Очерёдность изменений

1. Пробник и подтверждённые контракты Codex.
2. TargetProfile и сохранение поведения Claude.
3. Пакет Codex, setup и ручные навыки — первый полезный результат.
4. Нормализация событий и восстановимая очередь.
5. Llm adapter, автоматический анализ и доставка отчёта.
6. Evals, документация и выпуск.

Оценка полного локального варианта: 10–15 рабочих дней после начала исследования, затем неделя наблюдения. Это предварительная оценка: способ вызова модели и поведение hooks — главные источники неопределённости. Ручной вариант можно получить раньше, после этапов 0–2.

За рамками первого выпуска: OpenViking для Codex, равенство всех метрик с Claude, восстановление baseline из всей истории Codex, cloud, публичный каталог и отдельный MCP-сервер. Для основного локального цикла MCP пока не нужен; пересмотреть это, если подтверждённые ограничения загрузки контекста или вызова CLI потребуют другого интерфейса.
