# Archivist: выбор системы памяти и mem0 (облако и свой сервер)

Дата: 2026-10-29.
Ветка: `feature/memory-projection`.
Документ продолжает утверждённый план проекции журнала в память. Этап 1 (OpenViking) сделан и проверен вживую.

## Зачем

Пользователь работает с внешней долгосрочной памятью. Он хочет, чтобы все его агенты и плагины пользовались одними знаниями.

Этап 1 научил Archivist класть записи в OpenViking. Но системы памяти у людей разные: mem0, Hindsight, supermemory. Archivist должен класть знания проекта в ту систему, которой пользуется человек. Записи должны находить его другие агенты в этом же репозитории.

Систему памяти каждый выбирает сам, и в одной команде они могут различаться: у одного mem0, у другого OpenViking. Поэтому выбор хранится в личных настройках плагина. В `.archivist/config.json` ему не место: этот файл лежит в git и общий для команды.

mem0 бывает облачным и своим: сервер mem0 запускается из его репозитория в docker, например на `http://localhost:8888`. Облако — чужой сервис, поэтому знания проекта уходят туда, только когда человек явно включил этот проект. Свой сервер принадлежит человеку, как и OpenViking.

## Цели этого раунда

1. Настройки плагина: какая память, адрес сервера, API-ключ и список проектов, которые можно отправлять в облако.
   - Объявляются в `userConfig` в `plugin/.claude-plugin/plugin.json` и видны в `/config`.
   - По документации Claude Code спрашивает их и при установке плагина. В типах мода этого нет, проверим вживую.
2. Адаптер mem0 по тому же принципу, что и OpenViking:
   - текст пишется дословно;
   - у каждой записи свой ключ;
   - правила сведения не меняются.

   Он работает с обоими вариантами mem0: с облаком (`https://api.mem0.ai`) и со своим сервером по адресу из настроек.
3. Записи Archivist в облачном mem0 должен находить recall собственных плагинов mem0 для Claude Code, Codex и Cursor в этом же репозитории. Со своим сервером эти плагины не работают, см. «Адаптер mem0».
4. Сверка с облачным mem0 не должна расходовать квоту чтений: на проект уходит один запрос списка (несколько, если записей больше 200), без чтения записей по одной, и не чаще раза в сутки.
5. В облако уходят знания только тех проектов, которые человек явно включил. В новом проекте Archivist один раз подсказывает, как включить.
6. `/archivist memory`, health и лог показывают mem0 так же, как OpenViking: систему, проект, счётчики, последнюю ошибку. Для проекта, не включённого для облака, — что он не отправляется и как его включить.

## Не входит

- **mem0 как библиотека внутри другого инструмента**, без своего сервера. У мода есть только HTTP и MCP, до такой памяти он не дотянется.
- **MCP-сервер mem0.** Схема его инструментов не опубликована, запись асинхронная, а текст проходит через модель.
- **Этапы 2 (чтение) и 3 (сверка чужих правок)** из утверждённого плана. Они идут после этого раунда, сразу для OpenViking и mem0.
- **Следующие раунды:** сначала Hindsight и supermemory, потом basic-memory и MemPalace. Заметки для них — в конце документа.
- **Не планируются:**
  - claude-mem: в его MCP нельзя задать свой ключ и нельзя удалить запись;
  - Serena: пишет внутрь репозитория;
  - системы, которые хранят только извлечённые факты: Zep, Cognee, Graphiti, MemOS, Memori.
- **Общий слой памяти для многих агентов и для команды** отложен до реального использования.

## Чего нельзя допустить

- Ключ попадает в репозиторий, чат, лог, отчёт или текст ошибки.
- У человека, который не пользуется памятью, плагин не загружается. Причина была бы в обязательном поле `userConfig` без значения: оно ломает загрузку.
- Знания проекта уходят в чужое облако, пока человек не включил этот проект.
- Облачный ключ mem0 из окружения (`MEM0_API_KEY`) уходит на другой адрес, например на свой сервер.
- Записи пишутся в скоуп, где их никто не ищет: формально всё работает, но никто их не видит.
- Сбой mem0 (неверный ключ, квота, требование своего LLM-ключа) оборачивается повторами на каждом ходу или ломает анализ.
- В памяти появляются дубли одной записи, или записи теряются при смене системы памяти.

## Ограничения

- **Мод работает без Node:**
  - сеть доступна только через `$.http.fetch`;
  - окружение — через `$.env.get("ИМЯ")`, причём имя должно быть строковым литералом;
  - `$` передаётся только в функции верхнего уровня;
  - таймеры теряются при перезагрузке;
  - на `session.end` есть 1,5 с.
- **Настройки плагина** приходят в `register(on, options)` и не меняются, пока модуль активен. Изменение в `/config` перезагружает плагин, и `register` вызывается снова (`Register`, `PluginOptions` в `types/claude-code/index.d.ts`).
- **Хранение настроек.** Секретное поле `userConfig` хранится в системной связке ключей, остальные — в `settings.json` (`pluginConfigs[archivist].options`).
- **Поле `auth` в `$.http.fetch`** работает только для хостов Anthropic. Ключ mem0 модуль кладёт в заголовок сам.
- **Код без комментариев:** смысл передают имена.
- **Тесты** пишутся первыми, с подделками, без моков. `npm run check` и `claude plugin validate --strict` должны проходить.
- **Работа идёт этапами:** после каждого пользователь проверяет результат вживую.
- **Коммиты** — только по просьбе и без соавторства.

## Что решил пользователь

1. **Систему памяти выбирают в настройках плагина.** Полей три, и все необязательные:
   - какая память: `auto`, `openviking`, `mem0` или только файлы;
   - адрес сервера: пусто — облако mem0;
   - API-ключ: скрытое поле; если оно пустое, берётся `MEM0_API_KEY` из окружения.
2. **Поля общие для всех систем**, а не отдельный набор на каждую. Новая система — просто ещё один вариант в списке.
3. **`auto` работает как сейчас:** Archivist сам находит подключённый OpenViking.
4. **В mem0 Archivist ходит напрямую по REST** со своим ключом, а не через плагин mem0. Текст пишется дословно (`infer:false`), наш ключ — в metadata.
5. **В `.archivist/config.json` остаются только две настройки:**
   - `memory.enabled` — чтобы команда могла запретить выносить знания проекта в чью-то память;
   - `memory.project`.

   `memory.server` оттуда уходит.
6. **Порядок работ:**
   1. этот раунд: настройки и mem0;
   2. Hindsight и supermemory;
   3. basic-memory и MemPalace.

   claude-mem, Serena и системы только с извлечёнными фактами не планируются. Свой сервер mem0 сначала тоже был в этом списке, теперь он в этом раунде (п. 8).
7. **В облако уходят только явно включённые проекты.** Выбор mem0 в `/config` действует на всю машину, а Archivist работает в каждом репозитории, в том числе в закрытых рабочих. Поэтому проект попадает в облако, только когда человек его включил. Решение хранится в личном списке проектов в настройках плагина, а в новом проекте Archivist подсказывает `/archivist memory on`. Список — четвёртое поле настроек, тоже необязательное.
8. **mem0 бывает и локальным,** это нужно учесть.

## Как это устроено

### Настройки плагина

В `plugin.json` появляется `userConfig` с четырьмя полями. Имена выбирает строитель, например `memory`, `memory_url`, `memory_api_key`, `memory_cloud_projects`.

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| память | строка с вариантами `auto`, `openviking`, `mem0`, `off` | `auto` | куда класть записи |
| адрес | строка | пусто | пусто — облако mem0, `https://api.mem0.ai`; иначе базовый URL своего сервера mem0, например `http://localhost:8888` |
| ключ | строка, `sensitive` | пусто | ключ API; для облака пусто — `MEM0_API_KEY`, для своего сервера — только это поле |
| проекты для облака | список строк | пусто | какие проекты можно отправлять в облачную память |

Как работает каждое значение поля «память»:

- **`off`** — только файлы. В память ничего не уходит, даже если OpenViking подключён.
- **`auto`** — как сейчас: первый подключённый сервер OpenViking (`findOpenVikingServer`). mem0 так не выбирается, см. «Мои решения», п. 1.
- **`openviking`** — подключённый сервер OpenViking. Если его нет, синхронизации нет, и `/archivist memory` об этом говорит.
- **`mem0` с пустым адресом** — облако mem0, только для включённых проектов (следующий раздел). Ключ берётся из поля или из `MEM0_API_KEY`. Если ключа нет, синхронизации нет, и `/archivist memory` говорит, где его задать.
- **`mem0` с адресом** — свой сервер mem0, для всех проектов, как OpenViking. Ключ берётся только из поля. Без ключа запросы идут без авторизации. Так работает сервер с `AUTH_DISABLED=true`, остальные ответят 401.

Облако определяется по адресу: это пустой адрес, хост `mem0.ai` или его поддомены. Любой другой адрес — свой сервер.

Проектная настройка `memory.enabled: false` выключает синхронизацию независимо от личных настроек.

### Облако — только для включённых проектов

- **Что под это попадает.** Память, которая хранит записи в чужом облаке. Сейчас это только mem0 с пустым адресом. OpenViking и свой сервер mem0 работают, как OpenViking сейчас. Адаптеры следующих раундов сами сообщают, облако ли они при текущих настройках.
- **Поле «проекты для облака»** — личный список. Его элемент:
  - id проекта, как его показывает `/archivist memory`, например `github.com/owner/repo`;
  - префикс с `/*` в конце: `github.com/owner/*` включает все репозитории владельца;
  - `*` — все проекты. Это тоже явный выбор.
- **С чем сравнивается.** С действующим id проекта, с учётом `memory.project` из проектного конфига.
- **Команды.**
  - `/archivist memory on` добавляет текущий проект в список через `$.config.set`. После этого плагин перезагружается: так устроены настройки плагина.
  - `/archivist memory off` убирает проект из списка. Если проект включён префиксом или `*`, `off` говорит об этом и отправляет в `/config`.
- **Пока проект не включён,** в облако не уходит ничего: ни записи, ни удаления, ни сверка.
  - При первом старте сессии в таком проекте Archivist один раз подсказывает: выбрана облачная память mem0, этот проект туда не отправляется, включить — `/archivist memory on`.
  - `/archivist memory` и health говорят то же.
- **Клоны и worktree** подхватывают решение сами: проект определяется по remote, а список лежит в личных настройках, не в git.
- **`off` ничего не удаляет из облака,** как и отключение синхронизации, и напоминает про `/archivist memory clear`. `clear` работает и для невключённого проекта: убрать своё можно всегда.
- **Проектный `memory.enabled: false`** главнее списка.

### Адаптер mem0

Отдельный модуль рядом с `src/core/memory-openviking.ts`, без Node. Транспортом служит функция вида `http(method, path, body)`. В моде её подставляет `$.http.fetch`, в тестах — подделка.

У облака и своего сервера разные API, поэтому адаптер говорит на двух диалектах. Скоуп, metadata и правила у них общие.

**Скоуп.** Плагин mem0 для Claude Code держит логику в файле `memory_core.py`. Тот же файл стоит в плагинах для Codex и Cursor. Чтобы эти плагины находили записи Archivist, Archivist пишет с теми же id, что вычисляет этот файл:

- **`app_id`**: берётся `MEM0_PROJECT_ID`. Если его нет, то `<owner>-<repo>` из двух последних сегментов пути remote без `.git`. Если нет и remote, то имя папки.
- **`agent_id`**: `<app_id>-<первые 10 hex от sha256 нормализованного remote>`.
  - Нормализация повторяет `_normalize_remote` из mem0:
    - `git@host:o/r.git` превращается в `https://host/o/r`;
    - `.git`, учётные данные и `/` в конце убираются;
    - хост приводится к нижнему регистру;
    - схема остаётся как есть, поэтому у `ssh://` другой хэш.
  - Без remote: `local-<app_id>-<первые 10 hex от sha256 пути корня>`.
- **`user_id`**: берётся первое заданное значение из `MEM0_CODE_USER_ID`, `MEM0_USER_ID`, `MEM0_RESOLVED_USER_ID`, `USER`, `USERNAME`. Если ничего не задано — `"default"`. Это моё решение, см. «Мои решения», п. 2.

Тесты фиксируют эти вычисления на примерах: https, scp-подобный адрес, `ssh://`, без remote.

**Свой сервер.**
- У своего сервера нет `app_id`, остальные id те же.
- Плагины mem0 со своим сервером не работают. Они ходят только по путям облачного API (`/v3/memories/add/`, `/v3/memories/search/`, `/v2/memories/`), а у своего сервера таких путей нет.
- Записи на своём сервере видят:
  - его дашборд (`http://localhost:3000`);
  - инструменты, настроенные на этот сервер;
  - после этапа 2 — `/archivist recall`.
- Другие инструменты чаще всего ищут по `user_id`, поэтому он нужен и здесь. `agent_id` отделяет проект: по нему строится список.

**Операции:**

| Операция Archivist | Облако | Свой сервер |
|---|---|---|
| записать новую | `POST /v3/memories/add/` с `messages:[{role:"user",content:<текст>}]`, `infer:false`, `immutable:true`, `app_id`, `agent_id`, `user_id`, `metadata` | `POST /memories` с `messages`, `infer:false`, `agent_id`, `user_id`, `metadata` |
| изменить | добавить новую версию, затем удалить старую по UUID: `immutable` запрещает `PUT` | `PUT /memories/{id}` с `text` и `metadata`; консолидации там нет, id не меняется |
| удалить | `DELETE /v1/memories/{uuid}/`; 404 считается успехом | `DELETE /memories/{id}`; 404 считается успехом |
| список проекта | `POST /v3/memories/?page=N&page_size=200` с `filters: {AND:[{app_id},{metadata:{archivist_project:<проект>}}]}` и `fields: [id, memory, metadata, updated_at]`; страницы берутся, пока есть `next` | `GET /memories?agent_id=<agent_id>&top_k=1000`; фильтра по metadata и страниц нет, свои элементы отбираются по `metadata.archivist_project` |
| прочитать одну | тот же список с фильтром по `metadata.archivist_key` | `GET /memories/{id}`, если id известен из кэша, иначе список |
| авторизация | `Authorization: Token <ключ>` | `X-API-Key: <ключ>`; без ключа — без заголовка |

`top_k` на своём сервере передаётся явно. Без него сервер отдаёт 20 элементов, а больше 1000 не отдаёт совсем. Если пришло ровно 1000, health предупреждает, что список мог обрезаться.

**Metadata элемента** плоская, потому что облако mem0 фильтрует только по ключам верхнего уровня:
- `archivist_key` — `archivist/<проект>/<id>`;
- `archivist_project`;
- `archivist_id`;
- `archivist_updated`.

Подпись по-прежнему стоит и последней строкой текста, чтобы её видели другие агенты.

### Изменения в ядре (`src/core/memory.ts`)

- **`MemoryStore.list()`** может отдавать вместе с id и ref ещё и текст элемента. Если текст есть, `reconcile` в режиме сверки берёт его из списка и не вызывает `fetch` для каждой записи. Для OpenViking ничего не меняется.
- **`MemoryStore.put`** получает подпись записи: id, `updated`, проект. Так адаптер кладёт её в metadata, не разбирая текст.
- **`clearMemory`** удаляет по списку проекта и не читает записи по одной, если список уже отдал текст.
- **Дубли.** В списке могут оказаться два элемента с одним ключом: новая версия добавилась, а удалить старую не вышло, или две копии добавили запись одновременно. Сверка оставляет тот, что совпадает с журналом или новее, а лишние удаляет. Правило «чужое не трогать» не нарушается: это свои подписанные элементы.
- **Частота сверки.** Хранилище сообщает, тратят ли его чтения квоту: у облачного mem0 тратят, у своего сервера и у OpenViking — нет. Для такого хранилища сверка при старте сессии идёт не чаще раза в сутки на проект, а время последней сверки хранится в кэше. Ручной `/archivist memory sync` сверяет всегда. Перед записью изменённой записи её по-прежнему читают из памяти: это один запрос на запись, и он защищает от перезаписи более новой версии.
- **`memoryTarget`** в моде выбирает хранилище по личной настройке. Если хранилище облачное, он ещё проверяет, включён ли проект.
- **Кэш** по-прежнему отдельный на каждое хранилище: `.archivist/.local/memory-mem0.json` для облака и отдельный файл для своего сервера, свой на каждый адрес.
- **Смена системы памяти** ничего не удаляет из старой: её элементы остаются, кэш тоже. `/archivist memory clear` чистит текущую систему.

### Ошибки mem0

- **401/403** — ключ не принят. В `lastError` и в `/archivist memory` пишется, что mem0 не принял ключ. Синхронизация не повторяется до следующего старта сессии или ручного `sync`.
- **429 и ошибки квоты**, в том числе требование своего LLM-ключа после 30 дней бесплатного плана. Сообщение mem0 показывается как есть, но без ключа. Повтор — не раньше следующего старта сессии.
- **Сеть или 5xx** — как сейчас: сбой одной записи не мешает остальным, анализ от памяти не зависит.
- **Свой сервер не отвечает** (не запущен, неверный адрес) — так же, как сбой сети. `/archivist memory` пишет, что mem0 по этому адресу недоступен. Повтор — при следующей синхронизации.
- **Ключ не выводится нигде:** ни в лог, ни в ошибки, ни в `/archivist memory`.

- **CHANGELOG** и версия.

## Мои решения (проверь)

1. **`auto` не выбирает mem0,** даже если в окружении есть `MEM0_API_KEY`. mem0 — это облако, и Archivist сам отправляет туда данные. Поэтому mem0 включается только явным выбором.
2. **Пишу с `user_id`.** Тогда запись видна в общем канале проекта у плагина mem0 и в личном канале. Её видят и OpenCode с OpenClaw: они ищут по `user_id`. Цена такая: команда «забыть» плагина mem0 работает в личном канале и может удалить нашу запись. Archivist её не восстановит, а покажет как пропавшую — по принципу так и должно быть.
3. **`immutable:true` в облаке.** Консолидация mem0 (Dream) не сливает и не скрывает наши записи. Цена: изменить запись можно только удалив её и добавив заново, и она получает новый UUID.
4. **При изменении в облаке — сначала добавить новую версию, потом удалить старую.** Добавления могут подолгу не проходить: кончилась квота, или после 30 дней бесплатного плана mem0 требует свой LLM-ключ. Тогда в памяти остаётся прежняя версия, а не пустое место. Если старую удалить не вышло, остаётся дубль, и ближайшая сверка его уберёт.
5. **`~/.mem0/project_map.json` не читаю.** Это наследие старого плагина mem0, а мод не ходит в домашнюю папку. `MEM0_PROJECT_ID` поддерживаю.
6. **Облако или свой сервер — по адресу.** Пустой адрес, хост `mem0.ai` или его поддомены — облако. Любой другой адрес — свой сервер mem0 с его API. Пробных запросов нет. Облачное API на другом хосте не поддерживаю, пока не попросят.
7. **Раунд идёт до этапов 2 и 3,** потому что они строятся на выбранном хранилище и на новом `list()` с текстом.
8. **`memory.server` убираю из проектного конфига без миграции:** версия 1.4.0, где он появился, ещё не выпущена.
9. **Версия 1.5.0:** раунд добавляет новую возможность. Этапы 2 и 3 сдвигаются на 1.5.x.
10. **Сверка с mem0 — не чаще раза в сутки на проект.** Сверка запускается после каждого старта сессии, а сессия стартует заново и при каждой перезагрузке плагина. На бесплатном плане mem0 даёт 1000 чтений в месяц, и из той же квоты читает recall плагина mem0. Archivist не должен её выедать.
11. **Свой сервер mem0 — в этом раунде,** после замечания, что mem0 бывает локальным. Адрес и адаптер общие, свой сервер — второй диалект того же адаптера.
    - Сверено по `server/main.py` в репозитории mem0, последнее изменение 2026-10-05.
    - Старая заметка, что сервер игнорирует `infer`, устарела: она была про заброшенный образ на Docker Hub. `make bootstrap` собирает сервер из исходников, и `infer` там есть.
12. **Включение по проекту — только для чужого облака.** Свой сервер mem0 работает для всех проектов, как OpenViking: хранилище принадлежит человеку, адрес он вписал сам.
    - Оговорка: сервер mem0 считает эмбеддинги только через OpenAI или Gemini, поэтому текст записей уходит туда на обработку. OpenViking так же прогоняет ресурсы через свою LLM.
    - Если и для своего сервера нужно включение по проекту, это одно условие в `memoryTarget`.
13. **`MEM0_API_KEY` из окружения — только для облака.** На свой сервер уходит только ключ из поля, чтобы облачный ключ не попал на другой адрес.
14. **Элемент списка проектов** — точный id, префикс с `/*` или `*`. Без регулярных выражений.
15. **Пока проект не включён, в облако не уходят и удаления.** Записи, отправленные раньше, остаются до `/archivist memory clear`, как при отключении синхронизации.
16. **На своём сервере изменение — `PUT` на месте.** В облаке `immutable` защищает от консолидации, а на своём сервере консолидации нет, и id записи не меняется.

## Что не проверено и проверится вживую

- Что mem0 отвечает на повторное добавление того же текста в тот же скоуп: по документации он отбрасывает точные повторы по хэшу.
- Расходует ли запрос списка квоту чтений. Это покажут счётчики `GET /v1/stats/` до и после сверки.
- Нужен ли свой LLM-ключ для добавлений с `infer:false` после 30 дней бесплатного плана.
- Можно ли удалить `immutable`-запись.
- Свой сервер:
  - что отвечает `POST /memories` с `infer:false`, ждём `results[].id`;
  - отдаёт ли список `metadata` без изменений;
  - заменяет ли `PUT` metadata целиком.
- Как `/config` показывает поле-список и принимает ли его `$.config.set`.

Для живой проверки облака нужен аккаунт mem0 и ключ, хватит бесплатного плана. Для своего сервера нужны docker, `make bootstrap` в `server/` репозитория mem0 и ключ OpenAI или Gemini для эмбеддингов.

## Проверка

**Тесты:**
- вычисление скоупа на примерах;
- адаптер с подделкой HTTP по форматам из OpenAPI mem0: `results[].id` при `infer:false`, пагинация по `next`, ответы 401, 404, 429;
- `reconcile` со списком, который отдаёт текст: `fetch` не вызывается;
- дубли по ключу;
- изменение записи: сначала добавление, потом удаление; если удаление сорвалось, остаётся дубль, и сверка его убирает;
- сверка с облачным mem0 не чаще раза в сутки, а ручной `sync` сверяет всегда;
- выбор хранилища по настройкам: `auto`, `openviking`, `mem0`, `off`, `mem0` без ключа, `mem0` с адресом, проектный `memory.enabled: false`;
- выбор диалекта по адресу: пусто и `*.mem0.ai` — облако, остальное — свой сервер;
- свой сервер:
  - `PUT` на месте;
  - список по `agent_id` с `top_k=1000`;

  - `memory.enabled: false` главнее списка;

- ключ не попадает ни в лог, ни в ошибки.

**Сборка и плагин:** `npm run check`; `claude plugin validate --strict`, который проверяет и схему `userConfig`.

## Справка: облако mem0 (сверено 2026-10-28)

- **Добавление:** `POST /v3/memories/add/`.
  - С `infer:false` запрос синхронный. Ответ: `{"message":"Memories stored successfully","status":"SUCCEEDED","event_id":"…","results":[{"id":"<uuid>","data":{"memory":"…"},"event":"ADD"}]}` (OpenAPI).
  - Нужен хотя бы один entity id.
  - `immutable` исключает запись из консолидации.
- **Список:** `POST /v3/memories/`.
  - Параметры: `page`; `page_size` от 1 до 200, по умолчанию 100.
  - В теле: `filters` (обязателен хотя бы один entity id) и `fields`.
  - Ответ: `{count, next, previous, results}`.
- **Фильтр по metadata:** `{"metadata":{"key":"value"}}`. Операторы — только равенство, `ne` и `contains`, и только по ключам верхнего уровня.
- **Удаление:** `DELETE /v1/memories/{id}/`; пакетно — `DELETE /v1/batch/`, до 1000 записей.
- **Плагин mem0 для Claude Code** (`integrations/claude-code-plugin/core/memory_core.py`; тот же файл у плагинов Codex и Cursor):
  - ищет через `POST /v3/memories/search/` с `filters: {OR:[{AND:[{agent_id},{app_id}]},{AND:[{user_id},{app_id}]}]}` и `latest_only:true`;
  - пишет с `infer:true` и полями `agent_id`, `user_id`, `app_id`, `run_id`.
- **Цены** (страница цен):
  - бесплатный план первые 30 дней — 10k добавлений и 1k чтений в месяц;
  - дальше добавлять можно только со своим LLM-ключом, лимиты тогда 50k добавлений и 10k чтений;
  - без своего ключа добавления возвращают ошибку, поиск ограничен 1k в месяц.
- **Dream:** Supersede и Merge всегда включены и срабатывают на каждом добавлении. Слитые записи по умолчанию скрыты из чтения.

## Справка: свой сервер mem0 (сверено 2026-10-29)

По `server/` в репозитории mem0, последнее изменение 2026-10-05.

- **Запуск:** `make bootstrap` в `server/`.
  - Поднимает API на `http://localhost:8888`, дашборд на `http://localhost:3000` и Postgres.
  - Создаёт администратора и первый API-ключ.
  - Docker-образ собирается из исходников.
- **Модели:** эмбеддинги только через OpenAI или Gemini, LLM — ещё и через Anthropic. Ключ провайдера задаётся в `.env` сервера.
- **Авторизация:** `X-API-Key` или Bearer-токен дашборда. `AUTH_DISABLED=true` её выключает; по документации это только для локальной разработки.
- **Добавление:** `POST /memories {messages, user_id?, agent_id?, run_id?, metadata?, infer?}`. Нужен хотя бы один entity id.
- **Список:** `GET /memories?user_id|agent_id|run_id&top_k`. По умолчанию 20 элементов, максимум 1000. Фильтра по metadata и страниц нет.
- **Одна запись:** `GET /memories/{id}`.
- **Изменение:** `PUT /memories/{id} {text?, metadata?}`.
- **Удаление:** `DELETE /memories/{id}`. Ошибку «not found» сервер отдаёт как 404.
- **Поиск:** `POST /search {query, filters, top_k, threshold}`.
- `app_id` нет.

## Заметки на следующие раунды

- **Hindsight.**
  - Банк `coding-agent::{gitProject}` общий примерно для 20 агентов.
  - `document_id` — наш ключ. `get_document` отдаёт `original_text`. Удаление каскадное.

  - REST v5: `POST /ns/{namespace}/document` со своим `id`; замена текста — `PATCH`; список по namespace с `include.content`.

  - MCP не принимает ключей, поэтому подключаемся только через REST.
- **basic-memory.** Путь заметки — наш ключ, работа через MCP, как с OpenViking.
- **MemPalace.** Через MCP, поиск и удаление по `source_file`.
